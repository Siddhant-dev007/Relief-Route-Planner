# Relief Load-and-Route Planner

CSEG3053 Design and Analysis of Algorithms — Phase II
(Project 13: Disaster Relief Supply Distribution Platform)

An offline C17 command-line tool for a disaster-relief coordinator. It decides
**which supplies each truck carries** and **how each truck reaches its shelter
when roads are damaged**, and compares three loading algorithms on the same input.

## Requirements

- GCC with C17 support (tested with MinGW-w64 GCC 15.1 on Windows)
- GNU Make (`mingw32-make` on Windows)
- No internet connection or external libraries

## Build and run

From this folder:

```powershell
mingw32-make          # builds build/relief.exe
mingw32-make run      # builds and starts the application
mingw32-make check    # builds and runs all four test programs
mingw32-make clean    # removes build outputs
```

Run the program from this folder so it can find `data/` and write to `results/`.

## Algorithms

| Algorithm | Role | Time | Auxiliary space | Optimal |
|---|---|---|---|---|
| 0/1 knapsack DP | Primary loading algorithm (from Phase I) | O(nW) | O(nW) | Yes |
| Greedy by value/weight | Fast baseline | O(n log n) | O(n) | No |
| Least-cost branch and bound | Exact alternative with pruning | O(2ⁿ) worst case | O(nodes) | Yes |
| Dijkstra | Shortest routes; re-run after road closures | O(V²) | O(V) | Yes |
| Merge sort | Greedy order, shelter priority, ID index | O(n log n) | O(n) | — |
| Binary search | Shelter lookup by ID | O(log n) | O(1) | — |

Relief value of a package = shelter urgency × need severity (as in Phase I).

**Planning rule (one dispatch round).** Dijkstra finds which shelters can be
reached from the depot. Vehicles are taken largest first; each goes to the
reachable shelter that has received the fewest vehicles so far (ties go to
higher urgency, then larger population). The chosen algorithm decides that
vehicle's load.

## Datasets

| File | Contents | Origin |
|---|---|---|
| `data/scenario_normal.csv` | 5 shelters, 28 packages, 4 vehicles, 8 nodes | Hand-written sample |
| `data/scenario_shock.csv` | Same area: 3 roads destroyed (one shelter cut off), one vehicle out of service, reduced capacity, more demand | Hand-written sample |
| `data/scenario_stress.csv` | 40 shelters, 413 packages, 25 vehicles, 60 nodes | Generated by `tools/generate_stress.py`, seed 42 |
| `data/adversarial_greedy.csv` | Greedy trap: greedy 100 vs optimal 180 | Hand-written |

Benchmark datasets are generated in code (`benchmark.c`) with a fixed seed, so every
run is reproducible.

## Tests

`mingw32-make check` runs four programs (161 checks):

| Program | Covers |
|---|---|
| `test_algorithms` | DP and branch and bound against a brute-force oracle (180 instances); greedy never above optimum; merge sort stability; binary search; Dijkstra with closures |
| `test_planner` | All scenarios with all algorithms; capacity, uniqueness and route invariants; unreachable shelter; rerouting; fairness rule; adversarial file |
| `test_edge_cases` | Boundary (capacity 0, exact fit, all too heavy); invalid records; malformed CSV files with line numbers; island shelter; all roads closed |
| `test_stress` | 1,000 packages; the 413-package scenario; branch-and-bound worst case; repeated runs |

## Limitations

- One dispatch round: each vehicle makes a single trip to a single shelter.
- Vehicles are dispatched one after another, so the overall plan is not globally
  optimal even though each DP / branch-and-bound load is.
- DP memory grows with n × W; tables above 25 million cells are refused.
- Branch and bound is exponential in the worst case; it stops at 2 million nodes
  (reached on 200 correlated packages, where DP still finishes).
- Road distances are static; there is no live traffic, travel time or multi-trip
  scheduling. Supply units are kilograms.
